# Design Audit · 2026-08-13 · Copy density and iconography

Scope: a copy-and-iconography audit, not a full visual re-audit. It measures
every word the explorer renders on all 15 routes, classifies each explanatory
block against a slop rubric, and compares the transaction page against the
Cardano reference explorer's Classic and Flow views.

Method: text extracted from the live app on `localhost:3001` through a DOM walk
that computes visibility, so a block counts as visible only if it is not
`display:none`, not `sr-only`, and not inside a closed `<details>`. Screenshots
captured for 15 routes x 2 themes x 2 viewports. Reference screenshots captured
from the public Cardano explorer's transaction page, Classic and Flow sub-tabs.

A first pass measured rendered DOM text without the visibility filter and
overstated four findings by counting copy that sits behind collapsed
disclosures. Those are corrected below and the superseded numbers are named
where they mattered, because the correction changes which pages the work should
target.

## Verdict

The explorer's copy problem is narrower and deeper than it first appears. Across
14 routes outside the glossary a reader sees 1,048 words of explanatory prose,
and 310 of them are on the transaction page alone, with nothing there behind a
disclosure. The next-worst page has 129. Every other page sits between 31 and
94, which is competitive with the reference explorer. So this is not a
site-wide verbosity problem to be trimmed evenly: it is one page carrying 30% of
all explanation, generated by five repeating patterns. The flow diagram is the
one place where our model is better than the reference's and the copy
apologises for it anyway.

## What "AI slop" means here

A definition that can be applied by someone other than its author. Each pattern
has a test that returns yes or no, so the map below is reproducible rather than
a matter of taste.

| # | Pattern | Test | Instances |
|---|---|---|---|
| S1 | Narrating the obvious | Delete the sentence. Does the reader lose a fact that is not already in an adjacent badge, number, or stepper? | 7 |
| S2 | Explaining absence | The count is zero. Would a reference explorer render anything at all? | 9 |
| S3 | Defensive meta-commentary | Does the sentence describe the page's design, or defend a decision, rather than state a fact about the record? | 6 |
| S4 | Methodology in the viewport | Would a reader act differently knowing this? If it is for us, it belongs in the API response or the docs. | 5 |
| S5 | Legend dumping | Does the page render explanations for statuses that no row on the page currently has, **where the reader can see them without asking**? | 0 (withdrawn, see below) |
| S6 | Copy-paste leakage | Is the sentence factually wrong on the page it appears on? | 2 |
| S7 | Tooltip spam | Does more than a third of the labels in one view carry an info affordance? | ~12 above the fold on `/transaction` |
| S8 | Static hint contradicting the value | Does the hint still make sense when the value is null, zero, or unbounded? | 1 confirmed |
| S9 | Duplicate facts across bands | Does the same number appear twice in one viewport? | 3 on `/transaction` |
| S10 | Generic titling | Does the page title discriminate between this record and any other of its kind? | 4 |
| S11 | Product education inside the data product | Is the reader here to learn the protocol, or to look up a record? | 2 |
| S12 | Prose shipped from the API | Is user-facing English being generated in the backend? | 8 sentences |

S1 through S4 and S9 through S11 are the ones a language model produces by
default: they all come from the same instinct, which is to be helpful by
explaining rather than by showing. S6 and S12 are structural and will keep
regenerating prose until the structure changes.

**S5 is withdrawn.** The first pass counted 611 words of status legend across
the three bridge pages. Those legends render inside a collapsed `<details>`
(`src/components/ui/legend.tsx:19`), so a reader sees none of it until they open
"Status key". Opt-in depth is the correct pattern, and it is the pattern the
rest of the site should copy rather than the one it should remove. What survives
on those pages is the S6 defect alone.

Two of these are correctness defects, not style:

- **S6**, `src/lib/status-registry.ts:99`: "The deposit UTxO was spent into the
  Midgard ledger" renders on `/withdrawals` and `/forced-transactions`, where
  there is no deposit UTxO. Verified in the rendered output of both pages.
- **S8**, `src/app/transaction/[txHash]/page.tsx:159-164`: validity interval
  reads "Unbounded" with the hint "The ledger accepts this transaction only
  inside this slot range." Unbounded means there is no slot range.

## Iconography gap

Reference vocabulary on the transaction page, per UTxO row: a value chip with
the currency mark, the address link, then copy, credential, exchange, wallet,
and burn affordances, then the output index as a separate badge. At page level:
copy, share and bookmark on the hash, a clock on the date, a lock on the TTL, a
check on the confirmation count, a producer card, and a size bar showing the
transaction as a percentage of the block limit.

What we already have and should keep: identicons per address, copy on every
identifier, direction icons on the input and output columns, unspent badges,
the credentials disclosure, and status badges with their own iconography. Our
identicon is better than the reference, which has none.

What is missing, ranked by how often a reader wants it:

1. **Total output.** Absent from the transaction page entirely. It is the
   second row of the reference's overview card and the most-wanted number on
   the page.
2. **Relative age.** We render `2026-08-13 11:24:52 UTC` only. The reference
   renders `7d 3h ago` with the absolute timestamp beside it. Relative age is
   how a reader judges recency at a glance.
3. **Block link in the header.** Our block height is buried inside the journey
   as a stage label. It should be a link on the summary band.
4. **Size in context.** We render `383 bytes` bare; the reference renders
   `0.29kB` with a bar showing 1.82% of the block limit. A bar turns a number
   nobody can calibrate into one anybody can.
5. **Confirmation depth** for settled blocks, which we hold in the L1 index and
   do not show.
6. **Output index as a distinct badge.** Ours is appended to the outref string
   (`076a06f94f…4f20#0`) where the reference gives it its own chip.
7. **Per-address quick actions** on each UTxO row: open the address page, copy,
   inspect the stake credential. We have copy only.

The reference's flame and exchange icons are Cardano-wide features (token burn,
market data) with no Midgard equivalent, and should not be copied.

## The flow diagram

Our model is better than the reference's and the copy does not act like it.

The reference draws a Sankey: inputs as one red bar, outputs as green bars,
ribbons between them with width proportional to value. It is attractive, and it
implies an input-to-output attribution that the UTxO ledger does not record.

Ours (`src/components/ui/utxoflow.tsx`) draws inputs, a central transaction
node, and outputs, with bezier connectors on both sides. Edge width scales with
the square root of value so one large UTxO does not flatten the rest
(`src/lib/flowEdge.ts:15-32`), edge colour separates script from key addresses,
and unresolved edges are dashed in the warning colour. That is a correct
diagram of what the ledger actually says, and it already does what was asked
for: lines that point at where value came from and went to, in different
colours, with a legend at `utxoflow.tsx:243`.

The first pass reported three defects from source, without a screenshot,
because the dev server had been killed during capture. Two survived contact
with the rendered page and one did not.

1. **Withdrawn: "the connectors do not render below 1024px."** True, and not a
   defect. Below `lg` the grid collapses to one column and the diagram stacks
   vertically, so a left-to-right connector would point at nothing. Vertical
   connectors for the stacked layout are worth doing and are a design exercise
   in their own right, not a visibility toggle.
2. **Confirmed: the connectors were squeezed into a 56px gutter**
   (`utxoflow.tsx:290`), with `viewBox="0 0 100 100"` and
   `preserveAspectRatio="none"`, so a curve drawn across a square was
   compressed into a hook. Widened to 96px. Verified on the rendered page: the
   output side now fans two visibly distinct curves, the thicker one carrying
   11.99 ada and the thinner 3 ada, and the unresolved input renders as a
   dashed amber line.
3. **Confirmed: the 48-word apology** (`utxoflow.tsx:317`) sat directly under
   the legend that already encoded the same information. Replaced with one
   sentence naming the only fact the diagram's shape cannot carry.

A regression caught by the suite while fixing 3: the replacement sentence was
first folded into `FlowLegend`, which is `hidden lg:flex` because it describes
lines only the desktop layout draws. That silently dropped the sentence on
mobile, where it still applies. It now lives in its own component outside the
legend. `e2e/utxo-flow.spec.ts:83` is what caught it.

## Gap to 10

Density is the criterion with the most headroom and the clearest definition of
done: a reader opening any record page should reach the first real fact within
one screen, and should meet no sentence whose deletion costs them nothing. The
target table above is that definition made countable. The second gap is
calibration: several of our numbers (size, settlement time, admission latency)
are shown raw where the reference shows them against a scale, and a bar or a
depth count closes that without adding a word.

## Implementation follow-through · 2026-08-14

The subsequent implementation kept the existing Midgard transaction surface
and changed only the parts the review identified as misleading or needlessly
Cardano-wide:

- Midgard L2 transaction detail retains Overview, State (Table and Flow),
  Datums & redeemers, Events, Details, and Raw. Its first content now states a
  ledger-backed action and the summary includes block, time, total output, fee,
  and size.
- Empty Datums & redeemers and Events tabs are omitted. The Details tab now
  contains Midgard authorization and commitments, not a catalogue of absent
  Cardano features.
- Cardano L1 transaction detail now contains a CExplorer handoff, inclusion
  time, action count, and canonical Midgard actions. Generic Cardano UTxO,
  collateral, mint/burn, metadata, and raw-ledger tabs were removed from this
  page only.
- Scheduler actions use the canonical Aiken constructor layout at read time.
  No heuristic decoder, migration, backfill, or node change was introduced.
  The previously unclassified real transaction
  `6f07f695a7a3e0b3c7ebd48d803a7e6a03764d14bbb89e5fe41a086fa6a194c3`
  now resolves to a valid `rewindEndOfShift` Scheduler action.
- Deposit, withdrawal, and forced-transaction Cardano references open
  CExplorer directly. Deposits show the funding address only when it is the
  exact input named by the canonical deposit datum.
- Visitor copy was shortened across L1 and bridge headings, API examples,
  asset coverage, address detail, block evidence, and the footer. Assertions
  now protect facts and scope rather than deleted explanatory prose.

Live database verification after implementation: 9 headers, 2 L2
transactions, 8 deposits, 1 withdrawal, 0 forced transactions, 49 indexed L1
transactions, 66 L1 events, and 9 L1-observed headers. The L1 count supersedes
the earlier snapshot of 39 because the indexer has continued syncing.

### Review of the follow-through · 2026-08-14

Two facts were decoded and then dropped before reaching a reader. Both are the
same defect the audit named elsewhere: indexed, and not shown.

- `SchedulerAction` carries a `neglected` event for the two skipped-operator
  constructors, naming whether a deposit, a withdrawal or a transaction order
  was passed over. `db/l1.ts` did not map it, so the contract could not carry
  it and the sentence could not say it. A skipped shift is exactly the case
  where a user needs to know their event was left behind. Now mapped, carried
  as an optional literal on `L1MidgardAction`, and appended to both
  skipped-operator sentences.
- The scheduler datum's whole payload is which operator is on shift and since
  when. Both were decoded, attached to the action, and rendered nowhere. The
  scheduler action row now shows them.

Two things verified rather than assumed:

- The funding address is derived from the deposit datum's own `l1OutRef`, and
  the page prints "N funding addresses" rather than choosing one when a
  transaction has several. This satisfies the rule that an L1 source address is
  never invented from a single Cardano input.
- The scheduler redeemer is matched by script hash against the manifest family
  and the `spend` purpose, not guessed from purpose alone, so a transaction
  carrying several script executions cannot attribute the wrong one.

One measurement to distrust: `/api/l1/deposits` served `fundingAddresses` as

### Vocabulary and tooltips · 2026-08-14

**The rule for layer tokens, refined.** Cardano is the L1 and Midgard is the L2,
so writing both names the same thing twice. Which one a surface gets depends on
the job it is doing:

- **The chain name** when the job is identifying whose record this is: page
  titles, navigation, breadcrumbs, meta descriptions, table captions, search
  results, status explanations, stepper stages, metric tiles.
- **The layer token** only where the relationship is the point and both halves
  are on screen at once: the bridge direction chips, the `L1L2Badge` pairs, and
  paired columns such as `L2 txs` beside `L1 settlement`.
- **Neither**, where the token adds nothing at all. "Awaiting L1" became
  "Awaiting settlement" rather than "Awaiting Cardano".

215 user-visible lines carried a layer token or a chain name. 42 doubled them
("Cardano L1" 34 times, "Midgard L2" 8). All 42 are now single, plus 28 bare
tokens in prose and unpaired labels. The remaining tokens are the paired cases,
which is the shape established explorers use: a bare `L1 Status` column header
next to its L2 counterpart, defined nowhere.

**Tooltips now open above the trigger.** `updatePosition` preferred below and
flipped above only when it ran out of room. Opening downward covers the rows
underneath the label, which on a detail grid or a table is the data the reader
is trying to read. Above is now the preference and below the fallback; both
still clamp to the viewport. Measured on the rendered page: trigger at y=707,
panel at 642 to 699.

**Tooltip copy.** Most of the 48 glossary entries are precise technical help and
were left alone. Ten were not, and they failed in two specific ways:

- Describing the explorer instead of the protocol. "An unknown event remains
  visible as raw data instead of being guessed or silently omitted" is our
  decoder's ethics, not a definition of a protocol event.
- The dismissive not-X shape and forward absolutes: "returns schema-validated
  JSON rather than page markup", "without scraping the page", "never replaces
  comparing the address text", "is not a verified token logo".

Also removed: the literal "Context:" label above a record-specific note in the
tooltip panel. The rule above it already separates that note from the shared
definition, and a word naming the kind of information is not information.

### The measuring instrument is not trustworthy · 2026-08-14

The audit's "next audit" item said to re-measure with the visibility-aware
instrument and move it into the repo. The re-measurement ran and its output
should not be believed. Two defects, found while checking a result that looked
too good:

1. **It requires two stopwords per block.** The filter was tuned to catch long
   hedged prose. "Midgard contract activity observed on Cardano preprod, newest
   first" contains none of `the a an is are that this which it they you of to
   and not but so because once until when only its their`, so it scores zero.
   The instrument gets blinder as the copy gets plainer, which means it reports
   its largest cuts exactly where it is least able to see.
2. **It misses text split across nested elements.** `/l1` renders its subtitle
   twice in the served HTML and the instrument counted zero blocks on that
   route, so a nested span is enough to hide a sentence from it.

Both defects push the same way: they overstate reduction. The headline figures
in the "Copy inventory" table above are therefore a floor on the original prose
and not a measurement of what remains. No percentage should be quoted from a
re-run until the instrument counts rendered text nodes by their rendered
extent rather than by a stopword heuristic.

What is still safe to say from this session: the specific blocks named in "The
map" are gone from source, and the capability reasons are gone from the API
payload under test. Neither claim depends on the instrument.
