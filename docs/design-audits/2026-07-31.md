# Design Audit · 2026-07-31

Baseline audit. No previous report exists, so this run sets the rubric and the
scores every later audit compares against.

**Capture conditions.** Next dev server on :3000 against the e2e fixture backend
(`app/e2e/fixtures/server.mjs`, 40 blocks, 60 transactions across all seven
lifecycle statuses, 3 addresses, populated bridge tables). 64 screenshots at
1440x900 and 390x844, light and dark, in `/tmp/.../scratchpad/audit`. Two
caveats: fixture *values* are synthetic, so findings about how the UI handles
very long asset lists or extreme amounts are approximations until it runs
against preprod; and the amber "Network not configured" badge in every shot is
an unset `NEXT_PUBLIC_NETWORK` in the capture environment, not a product defect,
though its salience is a finding in its own right.

**Working-tree state.** The audit covers uncommitted work. The admission-timing
timeline and the block finalization timeline are implemented in the working tree
(`backend/src/db/transaction.ts`, `backend/src/db/block.ts`,
`app/src/components/ui/timeline.tsx`) and both render. Any earlier statement that
the explorer discards admission timings described the committed tree, not this one.

## Verdict

The explorer is well built and visually disciplined, but it scores lower than
its polish suggests because half its pages carry almost no information: the
blocks list does not even show block height, and the address history table has
two columns. The strongest thing in the product is the pair of timelines on the
transaction and block pages, which answer a question no EVM or Cardano explorer
answers, but they are not joined to each other: a transaction page cannot say
which block included it or whether that block is final on L1, so the
differentiator is half-built. The biggest risk is not aesthetic; it is that the
UI can state protocol state wrongly (two contradicting status maps) or drop it
entirely (a decode failure returns 422 and takes the known state with it).

## Findings

### P0 — communicates wrong or missing protocol state

**A. Two disagreeing sources of truth for status semantics.**
`components/ui/status.tsx:5-11` documents that its map contradicts
`lib/status-registry.ts` on `pending_commit`, `validating`,
`observed_waiting_stability` and `awaiting`, and that the *wrong* one renders.
This can tell a user the wrong thing about protocol state, which is a
correctness defect, not polish.
*Fix:* migrate the badges to the registry and delete the local map.

**B. A transaction that exists but cannot be decoded returns HTTP 422 and loses
everything.** `backend/src/server/routes/transaction.ts` catches the decode
failure and returns `422 { error, detail }`, discarding the status and admission
record it computed moments earlier, and it never had block linkage to begin with
(see finding C). The frontend renders this honestly
(`transaction-TXREJ-d-L-fold.png`) but cannot recover what it was not sent, so a
real on-chain transaction reads as a failed lookup.
*Fix:* return 200 with a partial-success envelope
(`{ txId, transaction: null, decodeError: { code, detail }, status, admission,
inclusion }`). The pattern already exists in this codebase:
`getTransactionsPageRoute` uses `decodeTransactionSafe` and returns a per-row
`decodeError` with 200. The single-transaction route is the outlier.

**C. The transaction page never says which block included it, or whether that
block is final on L1.** The route returns `transaction`, `status` and
`admission` only. There is no header hash, no height, and no join to
`pending_block_finalizations`, so the lifecycle stops at "Committed" and the
page cannot answer "is this final on Cardano L1?". The block page models
settlement fully; the transaction page cannot reach it. This is the single
largest gap between the product and its own differentiator.
*Fix:* join `blocks` on `tx_id` for inclusion, then
`pending_block_finalizations` on `header_hash` for settlement. Both queries
already exist.

### P1 — clearly hurting quality

**1. `SummaryBand` paints empty grid cells as solid grey blocks.**
`app/src/components/ui/summary.tsx:12-14` sets `gap-px` over a `bg-border`
container with `bg-surface` cells, so any cell the item count does not fill
renders as a filled rectangle. Block detail passes 7 items into a 4-column grid
(`block-BLK-d-L.png`, bottom right); address passes 3 (`address-ADDR-d-L.png`);
mobile's 2-column grid has it too (`block-BLK-m-L-fold.png`). It reads as an
unfinished loading state on the most important pages in the product.
*Fix:* render placeholder cells for the remainder, or drop the painted-gap
technique and use explicit borders.

**2. The undecodable-transaction page is 500px of empty space.** The UI half of
finding B: once the envelope carries status, admission and inclusion, the page
must render them and scope the failure to the body section that actually failed.

**3. The blocks list has no block height.** `blocks-d-D-fold.png` is a
two-column table of header hash and relative time. Height is the natural
identifier for a block, it exists in the database, and `BlocksPageRow`
(`contracts/src/block.ts:67-71`) does not carry it. Lowest-information page in
the product.
*Fix:* widen the row schema with height, transaction count and finalization status.

**4. Address history is two columns.** `address-ADDR-d-L.png`: transaction hash
and an output count. No time, no direction, no value, no status.
*Fix, in two tiers, because exactness differs.* Reliably available now:
timestamp, status, block, received outputs (decodable from produced outputs),
UTxO count, first and latest activity. Not reliably available: outgoing value
and net delta, because `backend/src/db/ledger.ts` documents that a transaction's
own inputs leave the ledger once applied, so "historical inputs will commonly be
unresolvable". Ship the first tier, label the second explicitly ("net change
unavailable: historical inputs pruned"), and never treat an unresolved input as
zero. Exact deltas would need an address-event or spent-output projection in the
node.

**5. Four bridge statuses look like the same badge.**
`deposits-d-L-fold.png`: Awaiting, Projected, Consumed and Finalized share pill
shape, size, weight and a 10%-tint treatment (`components/ui/status.tsx:126-131`),
differing only in hue at low saturation. Terminal and non-terminal states are
not separable at a glance, and the encoding fails for color-blind users.
*Fix:* vary shape or weight as well as hue; give terminal states a filled
treatment and pending states an outline.

**6.** Moved to P0 finding A (status registry contradiction).

**7. Currency symbol placement is inconsistent inside a single page.** Block
detail shows `₳ 9.4` and `₳ 8.445013` in the summary band but `4.222 ₳` in the
transaction table below (`block-BLK-d-L.png`).
*Fix:* pick one and enforce it in the `Amount`/`ValueCell` primitives.

**8. Hierarchy is inverted on the two highest-traffic pages.** The overview's
largest type is on cumulative totals; the transaction page's first and largest
summary cell is the fee. The timelines, which are the product's differentiator,
sit below both.
*Fix:* lead the transaction page with execution, inclusion and settlement state;
demote fee into technical details. Do not lead with a single "value transferred"
figure (see "Value language" below).

**9. Search is duplicated on the overview.** Identical placeholder, identical
⌘K hint, 190px apart (`home-d-L-fold.png`): header (`AppShell.tsx:60`) and hero
(`Overview.tsx:186`).
*Fix:* keep the hero on `/` and hide the header instance there, or drop the hero.

**10. Mobile overview is 2050px tall before the bridge section.**
`home-m-L.png`: two full-width metric cards then 14 near-identical rows.
*Fix:* two-column compact metrics, 4 to 5 rows per panel.

**11. Two different rejection timestamps on one page.** `rej-L.png` shows the
timeline entry "Rejected 11:52:17 UTC" and the reason card "At: 11:52:36 UTC"
(`terminal_at` versus `tx_rejections.created_at`).
*Fix:* show one, or label both explicitly.

**12. WITHDRAWN — the skip link exists.** The first draft of this report claimed
`AppShell.tsx` had no skip link. It does: "Skip to content" at
`AppShell.tsx:52`, targeting `main id="main"` at `AppShell.tsx:86`. The claim
came from a case-sensitive grep for `skip`. Global `:focus-visible` is correctly
defined at `globals.css:52-54`. Accessibility scaffolding on the shell is in
better shape than the draft implied; what remains unverified is contrast ratios,
200% zoom, and screen-reader output, none of which this audit measured.

### P2 — polish

**13. Native assets are raw and unformatted.** `address-ADDR-d-L.png` shows
policy IDs and hex asset names undecoded, and quantity `4500000000` without
thousands separators while ADA amounts are grouped.
*Fix, in three tiers of increasing cost.* (a) Printable decoding of asset-name
bytes and thousands-grouping of quantities: local, cheap, no dependency.
(b) CIP-14 fingerprints: computable client-side but not free, because no
hashing library is currently a dependency of `app`, `contracts` or `ui`
(Blake2b-160 would need adding), and Midgard's policy-id and asset-name
semantics must first be confirmed CIP-14 compatible. (c) Ticker, decimals and
logo: not derivable from raw identifiers at all, needs an authoritative metadata
source. Do not conflate the three.

**14. Row height jitter in bridge tables.** Rows carrying a `+3 assets` chip
wrap the ₳ symbol to a second line and grow taller (`deposits-d-L-fold.png`,
rows 5 and 9).

**15. Hero search has weak affordance in dark mode.** `home-d-D-fold.png`: the
fill nearly matches the page background; the header instance reads more clearly.

**16. Detail pages end abruptly.** Transaction and rejected-transaction pages
stop after their last card with a large gap before the footer, and offer no next
action.

**17. UTxO flow is two lists, not a flow.** `utxo.png` shows inputs and outputs
side by side with one arrow between. There is no total, no balance line, and no
label for the highlighted change output, so a visitor cannot see where the 9.501
₳ input went.

### P3 — ideas

**18.** No visual signature yet: the design is high-quality neutral developer
product. The tree/Norse motif from the website brand does not appear.

**19.** No `/blocks`-level activity chart or operational metrics anywhere.

## Gap to 10

**Hierarchy (5.9) and density (6.0)** are the two lowest scores and they share
one cause: the pages give their largest type and their best real estate to
totals and fees, and their smallest to lifecycle and value. Closing this needs
no new data on the detail pages, only reordering. On the list pages it needs the
wider row contracts in findings 3 and 4. This is the single largest available
gain in the whole audit.

**Spacing (6.9)** is dragged down by one bug (finding 1). Fixing it moves block
and address from 5.0 to roughly 8.0 on that criterion by itself.

**Color semantics (6.5)** needs the status system to encode state in more than
hue, plus the registry migration. A 9 here means a visitor can sort terminal
from pending states in peripheral vision.

**Responsive integrity (6.2)** is a compression problem, not a layout problem.
The hierarchy survives mobile; the page is simply too long to scan.

**What a 10 looks like on this site specifically: three questions, never one
badge.** Midgard has states no other explorer has to explain, and today they are
collapsed into a single status pill. Every record should answer three separate
questions with three separate answers, each with its own source and timestamp:

```text
Execution         Inclusion             Settlement
Accepted          Block #40             Awaiting L1 stability
```

For a transaction that means admission/execution status, L2 block inclusion,
that block's finalization stage, and whether the transaction is still reversible
from the user's point of view. The timelines already model execution and
settlement separately; what is missing is the join between them (P0 finding C)
and the refusal to overload one badge. That is the most defensible advantage
available, because competing explorers are not modelling these states at all.

**Value language must stay precise.** "Transferred ₳9.4" is not a claim this
data supports. Total outputs include change; inputs are frequently unresolvable.
Use labelled quantities instead: total outputs, inputs resolved 1 of 2, received
by this address, spent from this address, net known change, and an explicit "net
change unavailable, historical inputs pruned". A confident wrong number costs
more trust than an honest gap.

**Failure taxonomy.** The states below are materially different and must never
collapse into a grey rectangle or a generic error: data unavailable, not yet
recorded, not applicable, partially decoded, historical input pruned, API
unreachable, data stale, unknown future protocol status.

**Parity with Cardano explorers** (Cardanoscan, Cexplorer, Adastat) is mostly
findings 3, 4 and 13: block height as the primary identifier, richer list rows,
an address statement scoped to what is exactly knowable, printable asset names,
grouped quantities. Those need no new data source. CIP-14 fingerprints need a
hashing dependency and a semantics check first. Out of reach without changing
the read-only Postgres architecture: L1 confirmation depth, asset and policy
search, script and datum decoding.

## Recommended order

1. **Correctness and visible defects.** Status registry migration; state-class
   badge encoding beyond hue; reconcile the two rejection timestamps; convert
   the decode failure to a partial-success envelope; join transaction to block
   and finalization. Then `SummaryBand`, which is cheap enough to ride along.
2. **List-page parity.** Blocks (height, tx count, duration, finalization);
   transactions (status, height, fee, in/out counts, time); address (UTxO count,
   time, status, received value, explicit partiality); compact stage indicators
   in every row.
3. **Information hierarchy.** Lead detail pages with execution/inclusion/
   settlement; demote fee; drop the duplicate overview search; compress mobile;
   give detail pages a next action.
4. **Cardano-native comprehension.** Printable asset names with canonical hex
   retained; grouped quantities; CIP-14 after verification; asset wrapping; a
   real UTxO flow with totals, fees and unresolved-input disclosure.
5. **Power and trust.** Block-height search; filters and shareable URLs; export
   and raw affordances; operational signals (latest block time, time since
   latest block, finalization backlog, oldest unfinalized block, connected
   network, last successful refresh) and no invented "indexer lag"; preprod and
   pathological-data validation; task-based usability testing.
